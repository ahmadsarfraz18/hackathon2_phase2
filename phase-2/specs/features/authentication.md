## User Scenarios & Testing *(mandatory)*

### User Story 1 - Secure Signup and Signin (Priority: P1)

As a new user, I can create an account and log in using email/password via Better Auth to access my personal todo dashboard.

**Acceptance Scenarios**:
1. **Given** a new user, **When** they submit the signup form, **Then** an account is created in the database and they are logged in.
2. **Given** an existing user, **When** they submit valid credentials, **Then** they are authenticated and redirected to the todo list.
3. **Given** an existing user, **When** they submit invalid credentials, **Then** an authentication error is displayed.

### User Story 2 - JWT Issuance and API Access (Priority: P1)

As an authenticated user, the system issues me a JWT token so that I can make secure, stateless requests to the FastAPI backend.

**Acceptance Scenarios**:
1. **Given** a successful login, **When** the frontend receives the user object, **Then** a JWT token is issued containing the `user_id` and `email` claims.
2. **Given** an active session, **When** the frontend makes an API request, **Then** it must include the `Authorization: Bearer <JWT>` header.

### User Story 3 - User Isolation & Authorization (Priority: P1)

As a user, I must only be able to view and modify my own tasks to ensure privacy and data security.

**Acceptance Scenarios**:
1. **Given** User A is logged in, **When** they request `GET /api/tasks`, **Then** the backend returns only tasks where `user_id == User A`.
2. **Given** User A is logged in, **When** they attempt to access User B's task by ID, **Then** the backend returns `403 Forbidden`.
3. **Given** a request without a token, **When** any protected endpoint is accessed, **Then** the backend returns `401 Unauthorized`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Better Auth MUST be configured as the sole authentication provider in the Next.js frontend.
- **FR-002**: Upon successful login/signup, the system MUST issue a signed JWT containing `user_id`, `email`, and `exp`.
- **FR-003**: The JWT signature MUST be verifiable by the FastAPI backend using `BETTER_AUTH_SECRET`.
- **FR-004**: Frontend MUST attach the JWT to the `Authorization: Bearer` header for all backend requests.
- **FR-005**: FastAPI MUST validate the token's signature, expiration (max 7 days), and integrity on every protected request.
- **FR-006**: Backend MUST extract the `user_id` from the JWT claims to identify the user (never trust request body/params for identity).
- **FR-007**: Every API operation MUST enforce user isolation by verifying ownership of the requested resource.

### Success Criteria

- **SC-001**: 100% of protected routes return 401 for missing/invalid tokens.
- **SC-002**: Zero data leakage between users (403 returned for unauthorized access).
- **SC-003**: Authentication overhead adds < 30ms to API response time.
- **SC-004**: All user identities are cryptographically assured via JWT signature.

## Technical Design

### JWT Payload Structure
```json
{
  "user_id": "uuid-v4-string",
  "email": "user@example.com",
  "iat": 1736410000,
  "exp": 1737014400
}
```

### Security Flow
1. **Frontend**: Login via Better Auth -> Receive User Data -> Request JWT from Auth API endpoint.
2. **Storage**: JWT is typically stored in a Secure, HttpOnly cookie or transiently in memory for the session.
3. **Request**: `fetch(API_URL, { headers: { Authorization: "Bearer <JWT>" } })`.
4. **Backend**:
   - Middleware catches request.
   - Verifies JWT using `HS256` with `BETTER_AUTH_SECRET`.
   - Checks `exp` claim.
   - Extracts `user_id`.
   - Injects `user_id` into route dependency.
   - Query: `db.query(Task).filter(Task.user_id == current_user_id)`.
